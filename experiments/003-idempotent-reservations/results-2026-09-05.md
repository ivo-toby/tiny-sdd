## What this tests

Strong-model preparation and review, with Qwen and Gemma implementing three
connected tasks through ordinary Pi tools: validate input, maintain atomic/idempotent
reservation state, then expose a Request/Response API. This is a synthetic
brownfield fixture with nine seeded regressions, not a deployed inventory
product or a change to a real customer repository.

The primary prepared the feature contract, task packets and two experimental
skills, reviewed the reference and independent checks, and made all progression
decisions. Luna-max handled fixture/check/capture mechanics and audits. Only
the assigned participant wrote scored implementation and tests. All unattended
operator approvals were explicitly simulated; actual human feature acceptance
remains pending.

See [protocol](protocol.md), [feature](feature.md), [manual procedure](README.md),
and [experimental skills](skills/tinysdd-task/SKILL.md). These skills remain
experiment-local; the existing product skill and global configuration are
unchanged. The skill-creator guidance informed the narrow preparation/execution
role split, not a new controller.

not a standalone test exit status. The service revision did not run its corrected
regression before the production fix. These are recorded process limitations,

## Interpretation

The reviewed feature attempts support feasibility of the proposed role split
under these conditions. Review was productive workflow work, not a penalty for
supervision. It does not establish that TinySDD improves accuracy over a matched
control, that preparation is repeatable, or that the models can reliably deliver
arbitrary products. The same primary prepared the contract and reviewed results;
the held-out checks are a separate finite signal, not independent model consensus.

The useful artifact set is modest: one 7916-byte feature contract, three task
packets totaling 3981 bytes in v1 / 4539 bytes in v2, and a 1743-byte task skill.
However, participant tests/evidence grew substantially, and experiment preparation plus primary
review effort is not included in captured Pi wall. No end-to-end cost-saving
claim follows from model execution times.

Pi 0.84.4 used the user's exact Qwen and Gemma model IDs through the unchanged
LiteLLM configuration. Thinking was requested off but thinking blocks were observed.
Effective backend settings, sampling independence, response freshness, proxy
retries, token usage and monetary cost remain UNKNOWN. Zero streaming usage
fields are placeholders, not free execution. No static compiler run was available;
TypeScript correctness is source-reviewed, not compiler-verified.

## Decision and next useful test

Keep the bounded preparation/task roles and small artifact set as experimental
candidates. Do not install or promote a new product skill solely on this pilot,
and do not build a product controller. The preparation skill guided this
primary-authored contract; repeatable artifact generation was not independently
tested. Real operator approval and usability were simulated, not validated.

The concrete ownership witness is worth retaining for this fixture. Test
expectations, concurrency coverage and evidence still need semantic review;
more passing tests alone are not an acceptance criterion. See
[review lessons](../../docs/feature-review-lessons.md) and the proposed
[operator walkthrough](../../docs/operator-walkthrough.md).

Next, select a small held-out feature in a real repository with the operator.
Include strong-model preparation from the actual request/code, operator review
of the resulting decisions, bounded smaller-model implementation and independent
feature verification. Record preparation/review effort, not only participant
time. That is more discriminating than further samples of this same inventory
feature. A matched control is necessary for a claim that a particular skill or
packet change improves outcomes.

The six-minute task budget is an experimental bound, not a measured intrinsic
model limit or proposed product requirement. Timeout-related evidence gaps and
verbose participant artifacts motivate examining task/report size, not a claim
that less supervision or a new harness is required. Nemotron remains untested
on this feature; its earlier qualification issue is not evidence of inability
to implement the contract.
